Challenge 5 Writeup

RSA Near-Prime Factorization

cryptoRSAFermat factorization

The Vulnerability

Looking at the provided source code, the prime generation logic stands out immediately:

p = getPrime(2048)
q = p + 2
while not isPrime(q):
    q += 2

Normal RSA key generation picks p and q as two large, independently random primes of similar bit-length. Here, q is derived directly from p by walking upward in steps of 2 until the next prime is found. Since primes of this size are spaced (on average) only a few hundred integers apart, q ends up extremely close to p — typically within a few dozen increments of +2.

This is the classic setup for Fermat's factorization method, which is efficient precisely when the two factors of N are close together.

Why Fermat's Method Works Here

If N = p * q and p ≈ q, we can write:

a = (p + q) / 2     b = (q - p) / 2

so that N = a² - b² (a difference of squares). Since b is small (because p and q are close), we can find it by:

  1. Starting with a = ceil(sqrt(N))
  2. Computing b² = a² - N
  3. Checking if b² is a perfect square
  4. If not, incrementing a by 1 and repeating

The number of iterations needed is roughly proportional to how far apart p and q are — which, given the +2, +2, +2... search here, is tiny compared to the size of the primes themselves (2048 bits). This turns an intractable factoring problem into one solvable in a handful of iterations instead of astronomically many.

Implementation

Using gmpy2 for fast arbitrary-precision integer square roots:

from gmpy2 import mpz, isqrt

N = mpz(N)
a = isqrt(N) + 1
while True:
    b2 = a*a - N
    b = isqrt(b2)
    if b*b == b2:
        p = a - b
        q = a + b
        break
    a += 1

This found the factorization on essentially the first iteration (count = 0), confirming just how close p and q were.

Decrypting the Flag

With p and q recovered, standard RSA decryption applies:

phi = (p - 1) * (q - 1)
d = pow(e, -1, phi)          # modular inverse of e mod phi
m = pow(flag_enc, d, N)      # standard RSA decryption
flag = long_to_bytes(m)

Takeaway

RSA security relies on N's factors being unpredictably far apart in the space of possible primes. Any shortcut in prime generation that produces p and q close to each other — sequential search, shared high-order bits, small offsets, etc. — reduces factoring to a fast difference-of-squares search rather than requiring general-purpose factoring algorithms. The lesson embedded in the flag itself (ROOTED) is a pun: literally solved by taking integer square roots.

Challenge 8 Writeup

Race Condition to Command Injection

race conditioncommand injectionthreading

This challenge contained a command injection vulnerability caused by a combination of global mutable state, threading, and shell=True.

The Vulnerability

The application stored the user-controlled hostname in a global variable before validating it:

bird_song_host = input(...).strip()

for c in bird_song_host:
    if c not in "abcdefghijklmnopqrstuvwxyz0123456789.":
        print(f"'{c}' is not allowed")
        return

Although invalid characters were rejected, the malicious value had already been assigned to bird_song_host.

A worker thread repeatedly read this same global variable and executed a shell command:

for i in range(number_of_songs):
    command = f'echo "TODO: implement sending a bird song to {bird_song_host}"'

    running_task = subprocess.run(
        command,
        shell=True,
        capture_output=True,
        text=True,
        check=False
    )

    time.sleep(1)

Exploitation

  1. Started a worker using a valid hostname with 10 iterations. This kept the worker running long enough to exploit the shared global state.
  2. While the worker was still running, started another bird song request and entered the payload x"; cat flag.txt; echo "x.
  3. The application rejected the input, but the global variable had already been overwritten. On the worker's next iteration, the resulting command was approximately: echo "TODO: implement sending a bird song to x"; cat flag.txt; echo "x"
  4. Because shell=True was used, the injected command executed. Checking the bird song status then displayed the output, including the flag.

Key Takeaway

  • User input was stored before validation.
  • A worker thread could read the overwritten global variable.
  • The value was inserted into a shell command using shell=True.

Together, these issues turned an apparent input validation check into a race-condition-based command injection vulnerability.

Challenge 13 Writeup

NoSQL Injection

NoSQL injectionMongoDBblind regex oracle

The application exposed a POST /login endpoint accepting JSON username and password fields. Although the challenge claimed to have eliminated SQL injection, it was vulnerable to NoSQL injection because user-controlled JSON objects were passed directly into a MongoDB-style query.

The Vulnerability

The key was MongoDB's $ne operator, which means not equal. Instead of supplying strings, we supplied objects: 

{"username":{"$ne":null},"password":{"$ne":null}}

MongoDB interpreted this as a query for a user whose username and password were both not null, which matched the admin account and returned: 

{"success":true,"user":"admin"}
The underlying issue was insufficient input validation: the application expected strings but allowed arbitrary MongoDB query operators.

Blind Regex Extraction

We could then turn the password check into a blind regex oracle using MongoDB's $regex operator. For example: 

{"username":"admin","password":{"$regex":"^NZCSC\\{"}}

This returned success, proving that the admin password began with NZCSC{. We could test candidate characters by extending the regex: if ^NZCSC{s returned success while ^NZCSC{a did not, we knew the next character was s. Repeating this process allowed the password — and therefore the flag — to be recovered without directly reading the database.

Speeding It Up

Rather than testing every possible character individually, candidates can be split into groups using regex character classes such as [a-m]. A successful match tells us the next character is within that group, allowing a binary-search approach and reducing the number of requests to roughly log₂(n) per character.

Takeaway

The challenge combined two vulnerabilities: NoSQL operator injection to bypass authentication, followed by blind regex-based extraction of the flag from the admin password.
